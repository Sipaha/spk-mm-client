- Thread focus: хвост последних ответов — это `t.replies` фокусированного треда (не отдельное
  поле); `rev` растёт только от применённых данных, центрирование — по nonce UI.
- `jumpable` у результата только повышается при обновлении сайдбара той же команды (R14):
  сайдбар — отфильтрованный вид (скрытые DM/GM), покинутый канал даёт ошибку в карточке.
- Якорь страницы разрыва (Task 8, найдено e2e-проходом): сохраняется сторона, с которой
  читатель подошёл к строке разрыва (где строка была, пока была вне экрана), а не половина
  экрана, где она оказалась; пост под строкой держится нижним краем; обновление строк до
  прихода страницы (живой пост вытесняет старейший пост окна в разрыв) не сдвигает читаемое —
  и во время прокрутки колесом (поправка через `ScrollShift`, без записи `scrollTop`);
  строка, смонтированная виртуализатором уже после кадра прокрутки, тоже грузится.

## Решения пользователя (2026-09-30)

- Поиск по сообщениям **разрешён** (снимает запрет из `docs/backlog.md`). Ctrl+K — не делаем.
- Переход к результату — **полноценный**: к любому, даже старому сообщению, с окном вокруг
  него, догрузкой более новых и подсветкой.
- Область — **текущая команда текущего сервера** (`POST /api/v4/teams/{team}/posts/search`).
- В эту итерацию: подсветка найденных слов, подсказки `from:`/`in:`. В бэклог: «Файлы»,

  живые правки в уже показанных результатах.

## Факты API (Mattermost 10.11, по коду)

- `POST /teams/{team_id}/posts/search`, тело `{terms, is_or_search, time_zone_offset,
  include_deleted_channels, page, per_page}`; пустой `terms` → 400. Ответ — PostList
  (`order`, `posts`) + `matches`. Синтаксис (`from:`, `in:`, `before:`/`after:`/`on:`,
  `"фраза"`, `-исключение`, `слово*`) разбирает сервер.
- **Пагинация зависит от движка.** bleve (включён на целевом сервере, проверено
  2026-09-24) — честный offset `page*perPage` и заполненные `matches`
  (`platform/services/searchengine/bleveengine/search.go:214–222`). SQL-движок — `page > 0`
  всегда пусто, страница 0 — до 100 постов на группу параметров, `per_page` игнорируется
  (`sqlstore/post_store.go:2128`, `:2977`). Offset — не атомарный снимок. Правило клиента для
  обоих: `has_next` = сырая длина страницы ≥ `per_page`; `per_page = 20`.
- **Предел выдачи в клиенте:** не больше 25 страниц (`page` 0…24, ≤ 500 сырых результатов)
  за сессию поиска — ограничение памяти; достигнут при `has_next` на странице 24 → DTO
  `limit_reached`, UI — «Показаны первые результаты — уточните запрос». Это не «конец
  выдачи».
- **`matches` = `nil` у SQL-движка** (`sqlstore/post_store.go`) — наполняют только ES/bleve.
  Подсветка — по терминам запроса (аналог `parseSearchTerms` веб-клиента), `matches` —
  если есть, строго по id своего hit. У веб-клиента `\b` без флага `u` — кириллица не
  подсвечивается; у нас границы слов по Unicode.
- `in:`: канал — slug (`name`); DM — `in:@username`; GM — `in:@a,b,c` (ровно все участники,
  включая себя). `GET /posts/{id}` не-члену открытого канала своей команды отвечает 200.
- Посты канала: `GET /channels/{id}/posts?before=X|after=X&per_page=N` (ответ несёт
  `prev_post_id`/`next_post_id` — серверные курсоры конца), `GET /posts/{id}`.
- Тред: `GET /posts/{root}/thread?perPage=N&direction=up|down&fromCreateAt=T&fromPost=P`
  — листается в обе стороны (`api4/post.go` `getPostThread`, `post_store.go` Direction).

## Секция 1. Переход к сообщению в канале

### Модель: два сегмента и явный разрыв

У активного канала в Go: окно `Win` (последние ≤60, живое) и `s.older` — удерживаемая
история. Добавляется флаг `s.olderGap`: между `s.older` и `Win` есть незагруженная дыра.

**Инварианты** (проверяются тестами state):
1. `s.older` — всегда один непрерывный по серверу участок; дедуп по ID с `Win`.
2. Разрыв — только строго между `s.older` и `Win`; внутри `s.older` дыр нет.
3. `olderGap == false` ⇒ `s.older` примыкает к `Win` (как сегодня).

Следствия в коде:
- `trimWindowLocked` при `olderGap` **не** переносит вытесненные из окна посты в
  `s.older` (иначе дыра окажется внутри `s.older`) — они выбрасываются и вернутся
  догрузкой разрыва. Без разрыва — как сейчас.
- `MergeSince`: сначала обновление/удаление **всех уже удерживаемых копий** (Win и
  `s.older`, `newerOf`/`removeLocked`), затем отдельно — допуск в `Win` по нынешнему
  правилу (`CreateAt >= oldest`). Пост из since-строк, лежащий внутри дыры, в `s.older`
  не добавляется (он не заполняет дыру).
- `SetWindow` при дыре с прежним окном (overflow после реконнекта): **сегмент
  сохраняется**, `s.olderGap = true` (вместо сброса истории — читающий не выбрасывается
  вниз). Без удерживаемой истории — как сейчас.
- `SetActive` (смена канала), `ResetWindows` (смена CRT), забывание канала — атомарно
  сбрасывают `s.older`, `olderGap` и инвалидируют запросы (см. «Поколения»).
- В `ChannelView`: новое поле `gap: {open: bool, before_id: string}` — `open` — сам факт
  незакрытого разрыва, `before_id` — первый пост окна (может быть пуст, если `Win`
  временно пуст: удаления/перезагрузка — тогда строка разрыва рисуется в конце
  сегмента, а разрыв не считается закрытым). Отдельно от существующего `Win.GapAfter` (реконнект) —
  оба могут существовать одновременно, у строк разные ключи.

### Поколения (гонки)

Go: `s.histGen` — поколение истории активного канала. Увеличивается при смене активного
канала, новом переходе, сбросе сегмента, `ResetWindows`/смене CRT. Каждая операция
(`JumpTo`, `LoadOlder`, `LoadNewer`) захватывает `(histGen, курсор, crt)` под lock до
запроса и применяет страницу только если под lock всё совпадает. Покрывает
A→B→A, jump1→jump2, запоздалый `LoadOlder` поверх нового сегмента.
Фронт: `jumpSeq`; проверка **после каждого await** перед следующим шагом
(`openChannel` → `jumpTo` → прокрутка / `openThread`).

### Загрузка сегмента и закрытие разрыва

- `JumpTo(channel, post)`: пост уже в `Win`/`s.older` → без запросов. Иначе:
  `GET /posts/{id}` (проверка `channel_id`; 404/403 — ошибка «удалено или недоступно»),
  `before=id` и `after=id` по 30. `s.older` = сегмент, `olderGap = true`, если
  непрерывность с окном **не доказана**.
- `LoadNewer`: `after=<новейший ID в s.older>`, 60. Разрыв закрывается **только по
  доказательству**: сырая страница содержит ID, удерживаемый в `Win` (пересечение), или
  сервер сказал «дальше нет» (`next_post_id == ""`) и окно `Loaded && !Stale`. Счёт
  отфильтрованных (gone/OriginalID/CRT) постов и временные метки доказательством не
  считаются. Курсор — ID последнего **сырого** поста страницы, не отфильтрованного;
  удалённый курсорный пост → следующий запрос от предыдущего удерживаемого ID, с защитой
  от «нет прогресса» (две страницы без новых сырых ID → ошибка в строке разрыва с
  «Повторить», без автоповтора).
- `HasMore` (старее) сегмента — по `prev_post_id` страницы `before=`, как у истории.

### Лента (Feed)

- Строка разрыва «Загрузить более новые сообщения»: автодогрузка, когда видна, с
  бюджетом как у `fillViewportIfShort` (не больше N страниц подряд без действия
  пользователя; дальше — кнопка). Страницы грузятся **последовательно** (одна операция
  истории за раз на канал — в Go мьютекс операции, на фронте флаг).
- Якорь: pending-якорь привязан к версии применённой страницы (а не «любое обновление
  rows»); повторный захват позиции перед применением; при вставке в середину сохраняется
  видимый пост с той стороны, которая на экране (не считать всё prepend). WS-обновления
  до завершения REST не съедают якорь.
- Переход: синхронно выключает `atBottom`/`bottomTop`, сбрасывает старый якорь и
  pending-коррекции, flush `ScrollShift`; имеет приоритет над начальной прокруткой к
  «новым»/вниз/к ожидающему посту. Центрирование в виртуальном списке переменной высоты —
  `scrollToIndex` + DOM-коррекция после измерения. Повтор клика по тому же ID —
  с nonce запроса. Подсветка — акцентный фон, гаснет ~3 с.
- Прочтение: канал помечается прочитанным при открытии **при фокусе приложения, как
  сейчас** (`OpenChannel` зовёт view только если `Focused`; view перепроверяет
  Active/Focused/`NeedsView`), **даже если показан старый участок**. Линия «новые» строится перед первым
  загруженным чужим постом после `new_since`; если граница внутри дыры — линия не
  рисуется (точной границы не знаем) до догрузки.

## Секция 1б. Переход к ответу при CRT

Канал открывается на последних; справа — тред.
- Ответ среди удерживаемых (≤200 последних) → прокрутка + подсветка в панели.
- Иначе — **сегмент треда вокруг ответа**: корень + `direction=up` и `direction=down`
  страницы от целевого ответа (`fromCreateAt`/`fromPost`), курсоры с обеих сторон,
  потолок `ThreadMaxReplies` на сегмент сохраняется; между сегментом и последними
  ответами — разрыв «Загрузить более новые ответы» (те же правила доказательства). Это
  отдельный режим удержания треда (`thread.focus`), не повышение лимита 200 и не проход
  всех страниц. Живые ответы при разрыве копятся в хвосте последних и не вливаются в
  сегмент. «Открыть в браузере» ведёт на permalink **целевого ответа**.

## Секция 2. Интерфейс поиска

- **Поле** в шапке канала справа (перед загрузками), h-6, ~220 px (фокус/текст — ~320).
  **Ctrl+F** (физическая клавиша, `isShortcut`) фокусирует поле, если не открыт
  просмотрщик (любой, включая PDF), модальное окно, и событие не `defaultPrevented`.
  Enter — искать. Esc: сначала закрывает подсказки; затем в поле с текстом — очищает;
  в пустом — снимает фокус.
- **Подсказки** `from:`/`in:` — по токену под курсором; ↑/↓/Enter/Tab. Go `Autocomplete`
  сегодня channel-scoped (`AutocompleteScope`) — для поиска нужен team-scope текущей
  команды: `from:` — пользователи включая «прочих» (не в канале), `in:` вставляет
  **slug** канала (`name`), не display_name; DM — `@username`.
- **Правая панель** обобщается: `rhs: {kind:'thread',…} | {kind:'search'} | null`, одна
  за раз, общие ширина/сплиттер/оверлей <1024 px. Закрытие треда в Go (`CloseThread`,
  инвалидация `threadSeq`) отделено от закрытия поиска: `setChannel`/`openChannel`
  закрывают тред, но не поиск; переход «тред → К результатам» закрывает тред в Go.
- **Сессия поиска** хранится отдельно от видимой панели: `{server, team, submittedTerms,
  hits, page, hasNext, scrollAnchor, generation}`; черновик поля — отдельно (правка поля
  не меняет подсветку полученных результатов). В узком оверлее панель результатов
  показывает свою строку запроса (редактируемую) — поле шапки за панелью недоступно.
- Панель: шапка h-8 «Результаты поиска» + `×`; разделители дат; карточка — аватар,
  автор, время, канал (`~town-square` / `@bob` / группа), markdown с подсветкой,
  вложения строкой имён, «Ответов: N»; клик/«Перейти» — переход. Следующая страница (20)
  при подходе к низу. Состояния: загрузка, «Ничего не найдено», ошибка + «Повторить»,
  офлайн. Ошибка перехода (удалён/недоступен) — inline в карточке, остальные результаты
  остаются. Позиция списка — якорем (переживает смену ширины), не голым scrollTop.
- Результаты переживают смену канала и обычный refresh той же команды; смена
  сервера/команды (`setSidebar` сравнивает team) или выход — закрывают поиск.
- Esc в панели (фокус в ней, нет поповера) закрывает, как у треда.

## Уточнения реализации (Codex, к редакции 2 — обязательны)

1. **thread.focus — скользящее окно ≤200**, не прежний `capped=true`: догрузка `down`
   освобождает дальний край `up` и наоборот; вытесненное возвращается курсором
   (сохраняем курсоры обоих краёв); видимый якорь удерживается. Живой хвост последних
   ответов при разрыве ограничен отдельно (≤ `ThreadPage` = 60, старейшие из хвоста
   выбрасываются — вернутся догрузкой разрыва). Целевой ответ добавляется явно из
   `GET /posts/{id}` (страницы от курсора могут его исключать); проверяются `channel_id` **и**
   `root_id`. Закрытие/повторное открытие треда и новый focus инвалидируют запросы
   (поколение треда).
2. **Сохранённый сегмент после `SetWindow` по overflow — неактуален**, пока не перепроверен:
   since-догонка при overflow идёт только за последней страницей (`fetch.go`), правки/
   удаления в сегменте могли потеряться. Сегмент помечается `stale` (данные и позиция
   сохраняются), воркер перечитывает удерживаемый участок (алгоритм ниже) и сверяет:
   отсутствующие в перечитанном — удаляются, изменённые — заменяются (`newerOf`); watermark сегмента не продвигается вместе с `Win` до завершения.
   То же для thread focus. Регрессия «офлайн-правка/удаление в сегменте + since overflow».
   **Алгоритм перепроверки** (ревью плана, Codex): диапазон — от самого старого до самого
   нового удерживаемого сырого поста сегмента (`low`, `high`, оба края с `create_at`), набор
   удерживаемых ID и поколение фиксируются на старте. `GET /posts/{high}` (404 → удалён),
   затем страницы `before=high` (сервер листает и от удалённого курсора) до поста старше
   `low.create_at` или `prev_post_id == ""` — только тогда покрытие доказано и отсутствующие
   ID удаляются; иначе (ошибка, отмена, частичный ответ) сегмент остаётся stale и ничего
   не удаляется. Живые правки/удаления во время перепроверки не откатываются (`newerOf`,
   `gone`): на старте фиксируется `UpdateAt` каждого удерживаемого ID, и отсутствующий в
   страницах пост не удаляется, если его локальная копия изменилась после старта. `stale` сегмента независим от открытости разрыва: разрыв может закрыться
   раньше перепроверки; у строки — свой индикатор и «Повторить».
3. **Курсор `LoadNewer` — отдельный сохранённый raw after-cursor сегмента** (ID и
   `create_at` самого нового **сырого** поста страницы после нормализации порядка — не
   последний элемент произвольного `order`), продвигается даже страницей без видимых
   постов. Фейк отдаёт `order` в реальном порядке сервера (новые первыми), чтобы тест не
   скрыл переворот.
4. **Закрытие разрыва проверяется при применении под lock** и только для того же
   разрыва: у разрыва своё поколение (`gapGen`, растёт при каждом открытии разрыва и
   реконнекте — `MarkStale` тоже); ответ, начатый до нового разрыва/реконнекта, закрыть его не может.
   `next_post_id == ""` засчитывается только при `Win.Loaded && !Win.Stale` на момент
   применения.
