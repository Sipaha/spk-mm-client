# spk-mm-client — лёгкий десктопный клиент Mattermost

Дата: 2026-09-24. Статус: Этап 3, часть 1 (аватары и статусы, превью картинок
и текста, реакции) реализована и проверена e2e (2026-09-25). Этап 2 реализован
и проверен e2e (Playwright против браузерного режима с mmfake — 2026-09-24) и
сквозным финальным ревью (все находки исправлены, детали —
`docs/plans/2026-09-24-stage2-chat-core.md`, раздел «Execution notes»); живая
проверка на mm.citeck.ru пройдена 2026-09-25 (пользователь: «вроде все
работает»; сон/пробуждение — переподключение и догонка; память — см.
`docs/spikes/…` S4). Этап 1 — реализован и проверен на Linux (вход через
GitLab на реальном сервере, трей, уведомления — 2026-09-24).
Решения приняты пользователем в переписке; документ фиксирует итог, а не варианты.

## Зачем

Официальный Mattermost Desktop (Electron) тяжёлый и сбоит. Замер на машине
пользователя: ~490 МБ PSS сразу после старта с одним сервером (v6.1.0), дальше
растёт; позже с открытым чатом — ~315 МБ Private_Dirty (386 МБ PSS). 2026-09-24 он вообще перестал запускаться: `safeStorage` молча ждал
разблокировки связки ключей gnome-keyring (подробности — раздел «Уроки»).

Цель — свой клиент поверх REST API v4 и WebSocket Mattermost **без загрузки
веб-клиента Mattermost**, только с нужными функциями.

## Критерии успеха

- Собственная память клиента — **Private_Dirty всех его процессов**:
  ориентир ~150 МБ с 2–3 серверами и ~100 каналами (цель, не жёсткий предел —
  удобство важнее: экономия, замедляющая UI, не принимается); обязательно —
  без роста за час активной работы.
  Это то, во что реально обходится запущенный клиент. PSS показывается
  справочно: он включает долю общих библиотек WebKit/GTK/ICU, которые делятся
  с другими приложениями на WebKit, и зависит от того, что ещё запущено
  (решение пользователя, 2026-09-24). Замер — `scripts/pss.sh <pid>`.
- Переключение канала мгновенное — из памяти, без сетевого ожидания.
- Открыв канал из уведомления, пользователь видит это сообщение и историю перед
  ним, а не пустой канал.
- Работает весь день без перезапусков, сам переживает обрывы сети и сон.
- Linux, Windows, macOS.

## Обязательные функции

Несколько серверов; вход через GitLab SSO; команды и каналы с категориями
сайдбара; непрочитанные и упоминания; сообщения с markdown; треды (CRT);
реакции; файлы (загрузка, скачивание, превью); поиск; уведомления; трей.

## Что НЕ делаем

Звонки (Calls); плагины и их UI (Boards, Playbooks и т.п.); интерактивные
кнопки/меню сообщений ботов (показываем только текст и вложения); настройки
команд, администрирование, создание команд; офлайн-архив всей истории.

## Проверенные факты о сервере пользователя

Проверено 2026-09-24 запросами без авторизации:

- Mattermost **10.11.22**, поиск — bleve, `EnableSignUpWithGitLab=true`,
  `EnableCustomEmoji=true`.
- `GET /oauth/gitlab/mobile_login?redirect_to=mmauth://callback` → **302 на
  GitLab**: схема `mmauth://` разрешена (это дефолт
  `NativeAppSettings.AppCustomURLSchemes = ["mmauth://","mmauthbeta://"]`).
- `redirect_to=http://127.0.0.1:…` → **отказ** («Invalid custom url scheme»):
  loopback-редирект невозможен без правки конфига сервера.
- По данным spk-cockpit: персональные токены (PAT) на сервере выключены,
  админ конфиг менять не будет.

## Архитектура

**Один процесс** Wails v3 (`v3.0.0-beta.25`, `@wailsio/runtime` того же
номера — решение зафиксировано в «Риски и спайки», S3: beta вместо альфы
соседних проектов). Go-ядро + React-UI. UI общается с Go через Wails-биндинги
(`Call.ByName`) и события; тот же UI запускается в браузерном режиме
(`--browser`, HTTP-транспорт с bearer-токеном и Origin-guard) — для разработки
и e2e. Схема и двойной транспорт — как в spk-mail.

**UI никогда не ходит к серверу Mattermost напрямую.** Токены живут только в Go;
картинки/файлы/аватары отдаются по единому пути `/media/<srv>/<kind>/<key>`,
который обслуживает `internal/media` (дисковый кэш с лимитом 256 МиБ, LRU):
в desktop-режиме — через asset handler Wails (`AssetOptions.Handler`), в
browser-режиме — тот же обработчик за HTTP, доступ к нему защищён cookie
`spk_media` (HttpOnly, SameSite=Strict) или bearer-токеном — открытого прокси
к серверу Mattermost нет, путь строится только из проверенных ключей
(`TestBadRequests`, `TestMediaNeedsThePageCookie`). Реакции (сохранение и
снятие) — документированное исключение из правила «POST не повторяются при
сетевых ошибках»: оба запроса идемпотентны на сервере Mattermost, поэтому при
неоднозначном исходе (сетевая ошибка, таймаут, 5xx) оптимистичное состояние
реакции сохраняется и запрос повторяется с бэкоффом 2/5/15 с, пока воркер не
подтвердит исход или не исчерпает 4 попытки (тогда — откат); бэкофф тикает
только пока воркер «живой» — в офлайне ожидающая попытка не расходуется
впустую, а при возврате в «живое» состояние все ожидающие пары повторяются
сразу, не дожидаясь своего таймера, так что время офлайна не срезает 4
попытки; явный отказ (4xx) откатывает немедленно; переключение реакции
обратно во время неуверенного ожидания отправляет второй, тоже идемпотентный
запрос —
`internal/mmsync/react_test.go` (`TestReactionNetworkFailureIsRetriedKeepingTheClick`,
`TestReactionRetriedWhenTheWorkerIsLiveAgain`, `TestReactionFailingOnIsRolledBackAfterTheLastAttempt`,
`TestReactionToggledBackWhileWaitingIsSentAtOnce`), решение пользователя 2026-09-25.

## Данные и синхронизация

### Хранение

- **Горячий слой — в памяти Go** (не в webview). На канал — окно последних
  ~60 постов с реакциями и метаданными файлов (без самих файлов); кэш
  тредов (ниже); каналы, членства (непрочитанные), пользователи,
  категории, preferences. Оценка: пост ≈ 1–2 КБ → 100 каналов ≈ 10 МБ,
  300 каналов ≈ 35 МБ. Переключение канала читает только память.
- **Диск — снимок для холодного старта**, отложенная запись: изменения
  копятся и сбрасываются в SQLite одной транзакцией раз в несколько секунд и
  при выходе. Никакой записи на каждое сообщение. После рестарта клиент сразу
  показывает каналы из снимка и догоняет только дельту через `since`.
- **Вложения в памяти не держим.** Файлы/картинки — по запросу в дисковый
  кэш с лимитом размера (LRU). Заранее качаем только маленькие превью в каналах
  с непрочитанным — **не сделано в части 1 этапа 3** (превью качаются при
  показе ленты; см. `docs/backlog.md`, «Этап 3, не вошло в часть 1»).
- Картинки/фрагменты (`/media/`) запрашиваются у сервера только через «живой»
  воркер: офлайн, при переподключении и при `needs_reauth` кэш отвечает 404
  (не запоминается), а UI повторяет не загрузившиеся картинки, фрагменты и
  эмодзи, когда сервер снова становится живым. 401 на картинку/эмодзи не
  запоминается как отказ и ведёт воркер в повторный вход.
- **Видео и аудио — потоком, не через дисковый кэш** (Task 7, вариант A,
  решение пользователя 2026-09-27): `<video controls>`/`<audio controls>` в
  webview читают `GET /api/v4/files/{id}` сквозной передачей (`internal/media`,
  вид `stream`) с поддержкой `Range` (206), без записи в дисковый кэш и без
  буферизации в памяти — файлы большие, а кэш на 256 МиБ не для них; один
  HTTP-поток на элемент, отмена закрывает upstream. В browser-режиме поток
  идёт по обычному `/media/<srv>/stream/<id>` на loopback-сервере UI (тот же,
  что раздаёт `/media/`). В desktop-режиме WebKitGTK/GStreamer не умеет читать
  `wails://` (спайк S6) — отдельный HTTP-сервер `internal/media.Loopback`
  слушает `127.0.0.1:0`, поднимается лениво при первом запросе адреса потока
  (`MediaStreamBase`) и живёт до выхода; URL несёт сессионный токен (32
  случайных байта, base64url, сравнение за постоянное время, новый при каждом
  запуске, не пишется в логи): `http://127.0.0.1:<port>/<token>/<srv>/stream/<id>`.
  Защиты: проверка `Host` (без DNS rebinding), только `GET`/`HEAD`, без CORS,
  `Cache-Control: no-store`, только белый список медиатипов. Играет одновременно
  только один элемент (запуск другого ставит предыдущий на паузу); уход
  элемента из DOM останавливает его и освобождает (`removeAttribute('src');
  load()`) — иначе WebKit держит декодер и буферы (урок 13b).
- **Скачивание, «Открыть» и список загрузок** (Task 4/5, часть 1 этапа 3):
  каталог — `SPK_MM_CLIENT_DOWNLOADS`, иначе XDG-каталог загрузок
  (локализованный, `~/Загрузки`), но не сам `$HOME` (запись `"$HOME/"` в
  `user-dirs.dirs` отключает каталог — тогда `~/Downloads`). Файл пишется в
  скрытый `.<имя>.part` и получает свободное имя без замены существующих;
  повторные клики по файлу, пока он качается, присоединяются к той же загрузке
  (одна копия). «Открыть» отдаёт системе только инертные типы из allowlist
  (растровые картинки, PDF, текст/лог/csv/json/md, макро-свободные офисные
  документы, аудио/видео, архивы); остальное (скрипты, лаунчеры, HTML/SVG,
  файлы без расширения) только сохраняется — решение 2026-09-25: файл пришёл
  от другого человека, а обработчик по умолчанию — `xdg-open`/ShellExecute/
  `open(1)`. Каждая загрузка — запись в SQLite (последние 100, id не
  переиспользуются), читается по запросу UI (кнопка «⬇» в шапке канала
  открывает панель списка, её accessible name несёт число активных —
  «Downloads» / «Downloads — active: N»); прогресс — событие не чаще ~4 раз в
  секунду на загрузку. «Показать в папке» — D-Bus `FileManager1.ShowItems`
  (таймаут 2 с), при ошибке — открытие каталога тем же opener'ом, что и
  «Открыть»; строка панели убирается действием «Убрать из списка», не трогая
  файл на диске.
- Прокрутка вверх за пределы окна — подгрузка страницами (`before`), в память
  на время просмотра канала; окно в снимке не растёт.
- **Кэш тредов — только в памяти, с явной границей** (план тредов
  `docs/plans/2026-09-28-threads.md`): не больше 3 тредов на сервер — открытый
  в панели и 2 недавних (LRU, вытесненный освобождается целиком); в каждом
  корень и не больше 200 ответов. Тред грузится последними 60 ответами
  (`GET /posts/{root}/thread?perPage=60&direction=up`, никогда без `perPage` —
  иначе сервер отдаёт тред целиком), прокрутка вверх догружает по 60 до
  потолка в 200. Закрытие панели обрезает тред до последних 60. Кэш не пишется
  в снимок и не восстанавливается на старте; очищается при остановке воркера,
  смене CRT и уходе из канала. После разрыва WS треды помечаются устаревшими,
  открытый перечитывает последнюю страницу. Черновики ответов — тоже только в
  памяти, не больше 50 (вытесняется дольше всех не тронутый). Замер: 30 тредов
  по 200 ответов, открытых и закрытых подряд, — куча Go после GC возвращается
  к исходной (+0,1 МБ; спайк тредов, «Замеры»).
- **Чужие статусы присутствия в снимок не пишутся** — только опрос в живом
  сеансе (см. «Живые обновления»); при холодном старте их точки появляются
  после первого опроса, а не из SQLite. Собственный статус — исключение: он
  часть снимка (`meta.Status`) и сразу восстанавливается в карту присутствия
  при рестарте (`presence[me]`), так что своя точка видна сразу, без ожидания
  опроса.

### Старт сервера

Параллельно в пределах лимита запросов: `users/me`, `users/me/teams`,
`users/me/teams/unread`; по командам — каналы, `channels/members`, категории
сайдбара, preferences, счётчики тредов (CRT).

Итоги упоминаний в тредах (только при CRT) читаются в составе тех же
метаданных, в горутине воркера — на пути старта ничего нового:
`users/me/teams/unread?include_collapsed_threads=true` (`thread_mention_count`
по командам, без DM/GM-тредов) и DM/GM-часть — `…/teams/{текущая}/threads?totalsOnly=true`
минус тот же запрос с `excludeDirect=true`. До них бейдж — без тредов. Ошибка
чтения итогов не фатальна (сохраняются прежние), кроме 401 и дедлайна. Дальше
итоги двигают дельты `unread_mentions − previous_unread_mentions` из
`thread_updated`/`thread_read_changed`; событие, пришедшее, пока итоги читались
(guard обновления), не прибавляется, а вызывает перечитывание итогов — оно
заменяет их целиком, если за время запроса их не сдвинуло другое событие.
`thread_read_changed` без `thread_id` («прочитано всё» на другом устройстве),
`thread_follow_changed` (отписка на другом устройстве — единственное событие о ней) и
`thread_updated` без `previous_unread_mentions` («непрочитано отсюда»,
`MarkChannelAsUnreadFromPost`) — тоже перечитывание, без дельты. Неудачное
перечитывание помечает итоги «грязными»: воркер перечитывает их при следующем
переходе в `live` (и resume тоже). Упоминания в тредах поднимают бейдж сервера (Σ по командам +
DM/GM-часть) и строку команды, но не строку канала; непрочитанные треды без
упоминаний бейдж не поднимают. Без CRT итогов нет.

### Предзагрузка постов (сразу, в фоне)

Приоритет: DM и каналы с упоминаниями → каналы с непрочитанным → треды с
непрочитанными ответами → недавно активные (`last_post_at`) → остальные
каналы пользователя. Для закэшированных — дельта `since`; для новых —
последние ~60 постов. Полная первичная загрузка — один раз, фоном.

Нюансы API (из опыта spk-cockpit): `since` — в миллисекундах, отдаёт до ~1000
постов и не сочетается с `before`/`per_page`; системные посты (`type`
`system_*`) приписаны не автору; файлы читать и из `file_ids`, и из
`metadata.files`; у tombstone удаления бывает `delete_at=0` — ориентир
`update_at`.

### Живые обновления

Один WebSocket на сервер. **Каждый пост из WS сразу пишется в горячий слой для
любого канала**; уведомление показывается после записи. Обрабатываемые события:
`posted`, `post_edited`, `post_deleted`, `reaction_added/removed`,
`channel_viewed`, `multiple_channels_viewed`, `post_unread`, `thread_updated`,
`thread_read_changed`, `thread_follow_changed`, `typing`, `status_change`,
`channel_created/updated/deleted`, `user_added/removed`, `direct_added`,
`group_added`, `sidebar_category_*`, `preferences_changed`, `user_updated`,
`emoji_added`, `hello`.

### Разрывы

- Переподключение с `connection_id`+`sequence_number` — сервер досылает
  пропущенное. Если досылка невозможна (буфер сервера потерян, новый
  `connection_id`) — ресинк: обновить `channels/members`, догнать каналы
  через `since`, применяя правки и удаления к уже известным постам.
- Начало дыры — момент, когда закончился последний поток, про который
  известно, что он непрерывен. Метка «живы до» (и её копия в снимке) не
  двигается, пока новый поток не доказан: resume принят (событие с
  ожидаемым `seq` или 3 с без `hello`, пока ни одно событие не удержано
  обновлением метаданных) или завершён ресинк; до первого доказательства
  начало дыры — `live/at` из снимка. Поэтому отказ в
  resume после долгого офлайна догоняет каналы с начала дыры, а не с
  момента переподключения. Сервер, трижды подряд закрывший resume до
  доказательства, получает свежее подключение с полным ресинком.
- Обновление метаданных (вступили в канал, новый DM, категории) выполняет
  цикл событий: пока идёт REST-чтение, события копятся и применяются после
  него под «охраной» `last_post_at` — счётчики не откатываются и не
  удваиваются. Обновление ограничено 45 с (иначе бросается целиком, события
  применяются, обновление повторяется через 5 с с удвоением до 60 с);
  команда, чьи категории не прочитались (500/403/сеть), сохраняет прежние; после «неустоявшегося» чтения —
  не больше одного дополнительного обновления. Пост в ещё неизвестном канале сохраняется и применяется
  после обновления (уведомление о первом сообщении нового DM не теряется).
  Уведомление зависит от новизны поста, а не от того, изменил ли он
  счётчики.
- На канал храним отрезок, про который известно, что история в нём
  непрерывна. При дыре (долгий офлайн) канал открывается с тем, что есть;
  индикатор загрузки — только в месте дыры.
- Профили пользователей из снимка (или пережившие разрыв) после каждого
  bootstrap один раз перечитываются в фоне — `users/ids?since=<начало дыры
  − 2 мин>` (сервер отдаёт только изменённые; смена аватара двигает
  `update_at`), без метки — все, пачками по 100: иначе аватар и имя,
  изменённые в офлайне, оставались бы старыми до живого `user_updated`.
- Машина состояний сервера: Off → Connecting → Live → Reconnecting (backoff
  1 с → 60 с) → NeedsReauth. Сон/пробуждение и смена сети — немедленная
  попытка переподключения.

### Прочтение

`channels/members/me/view` — только если окно в фокусе и канал на экране.
Фокус учитывается только для активного сервера — фоновые серверы не
считаются в фокусе, даже если окно приложения активно (иначе открытый канал
фонового сервера читался бы без того, чтобы пользователь его видел).
«Отметить непрочитанным» с поста. Непрочитанные под CRT считаются по
`*_root`-счётчикам.

Треды при CRT читаются отдельно: `PUT users/me/teams/{team}/threads/{root}/read/{ts}` —
только пока панель треда открыта (над его каналом), окно в фокусе и сервер
активный; при открытии, при получении фокуса, на новый чужой ответ и на
`thread_updated` открытого треда, пришедшая страница (читается только загруженный
тред). Один запрос на тред за раз с перепроверкой; `ts` — `create_at` новейшего
показанного ответа (свои часы — только у треда без ответов), так что часы, спешащие
относительно сервера, не помечают прочитанными ещё не показанные ответы, а повтор без
нового чужого ответа не шлётся. Результат запроса, пришедший после закрытия и нового
открытия панели, к новому открытию не относится.
`team` — команда канала, у DM/GM — текущая. 404 (не подписан на тред) — молча и
больше не слать для этого открытия, пока не придёт свой ответ или `thread_updated`
по нему. Автоматических повторов нет. Ответ `PUT` счётчики не трогает — только
событие `thread_read_changed`. Без CRT треды отдельно не читаются: всё делает
`view` канала.

## Уведомления

Решение «уведомлять ли» — по правилам сервера, а не по разбору текста:

- кто упомянут — из серверного поля `mentions` события `posted`;
  `@channel/@here/@all` с учётом `ignore_channel_mentions`;
- уровень: пользовательский (all / mention / none) и переопределение канала
  в `notify_props` членства; приглушённые каналы молчат;
- DM/GM уведомляют всегда (если не приглушены);
- не уведомлять: свой пост; канал открыт и окно в фокусе; статус DND; при
  CRT — ответ в треде, открытом в панели, при фокусе («тред открыт»; ответ в
  другом треде уведомляет);
- серия сообщений склеивается в одно уведомление (серия ответов одного треда —
  отдельно от канала: `ID` уведомления `mm-<srv>-<канал>-<корень>`);
- клик → окно на переднем плане, открыт канал; у ответа (оба режима) — затем
  его тред (`open_channel` несёт `root_id`).

Доставка: Linux — D-Bus `org.freedesktop.Notifications` (с действием по клику,
как в spk-mail); Windows — toast; macOS — UNUserNotificationCenter. Если
сервис уведомлений Wails v3 покрывает все три ОС с обработкой клика —
используем его (проверяется спайком S2).

Трей: сумма упоминаний по всем серверам + отдельный признак «есть
непрочитанное». Закрытие окна сворачивает в трей; на Linux без рабочей
D-Bus трея нет, и закрытие окна завершает приложение (см. S3).

## Интерфейс

- **Слева**: колонка серверов с бейджами; сайдбар команды — переключатель
  команд, категории сайдбара с сервера (Избранное, Каналы, Личные сообщения,
  пользовательские), поиск. Раздела «Треды» в сайдбаре нет (решение
  пользователя 2026-09-28): тред открывается в панели справа из ленты или по
  уведомлению.
- **Центр**: шапка канала (название, заголовок, участники); виртуализированная
  лента (группировка подряд идущих сообщений автора, разделители дней, линия
  «новые»); редактор.
- **Справа**: выезжающая панель — тред, результаты поиска, закреплённые,
  сведения о канале. **Панель треда** (план тредов) — 420 px справа от ленты,
  в окне уже 1024 px перекрывает ленту с кнопкой «← К каналу»: корень,
  разделитель «Ответов: N», ответы и свой редактор (фокус в нём при открытии).
  Открывается строкой «N ответов» под корнем, кнопкой «Ответить в треде» в
  панели действий поста и кликом по уведомлению об ответе; открытие другого
  треда заменяет текущий; закрывается `×`, Esc (фокус в панели, нет открытого
  поповера), сменой канала или сервера. Удалённый корень — баннер «Исходное
  сообщение удалено» и выключенный редактор. Тред длиннее 200 ответов —
  строка «Показаны последние 200 ответов» со ссылкой «Открыть в браузере».
  При CRT открытый тред помечается прочитанным на сервере, пока окно в
  фокусе (см. «Прочтение»). Без Follow/Unfollow, аватаров участников и линии
  «новые» (`docs/backlog.md`).
- **Пост**: markdown уровня Mattermost (код с подсветкой, таблицы, цитаты,
  упоминания, эмодзи вкл. кастомные, ссылки, серверные превью ссылок);
  вложения — картинки с превью и просмотрщиком (колесо — зум вокруг курсора,
  перетаскивание — пан, двойной клик — вписать/100%, оригинал грузится сразу
  рядом с превью), текстовые файлы фрагментом (до 64 КиБ в ленте, до 1 МиБ и
  с поиском в просмотрщике), markdown-файлы отрендеренным фрагментом
  (переключатель «Оформление»/«Исходный текст» в просмотрщике), видео —
  рамкой с постером и плеером по клику, аудио — компактным плеером в строке
  файла (играет всегда один элемент одновременно), прочие файлы — карточкой;
  реакции — чипы (высота 28 px, эмодзи 18 px) и пикер, кнопка «добавить
  реакцию» у чипов — того же размера с иконкой `IconAddReaction`; панель
  действий по наведению рендерится только у «горячего» поста (наведение/
  фокус или открытое своё меню «…»/пикер — иначе скрытый тулбар в каждой
  строке грузил бы картинки чужих быстрых реакций), кнопки 32×32 с иконками
  20 px, слева направо: до 3 быстрых реакций (`getOneClickReactionEmojis`
  веб-клиента — первые 3 известных имени из `recent_emojis`, пусто — ни
  одной; повторный клик по уже нашей реакции снимает её) | добавить реакцию
  | сохранить (`IconBookmark`/`IconBookmarkFilled` + акцентный цвет —
  предпочтение `flagged_post`, без отдельного экрана «Сохранённые», см.
  backlog) | ответить в треде (`IconReply`: у корня открывает его тред, у
  ответа — тред его корня; нет у ожидающих, неотправленных и системных
  постов) | «…» (Отметить
  непрочитанным, Копировать ссылку, Изменить/Удалить — последние два только
  у своих несистемных постов). «Закрепить» — не реализовано (см. «Справа»
  выше: закреплённые сообщения ждут панели справа). Под корнем с ответами (в
  обоих режимах CRT) — кликабельная строка «Ответов: N · последний ответ
  <время>», открывающая тред. При CRT в ленте только корни; без CRT ответы
  идут в ленте, и у первого ответа серии (предыдущая строка — не его корень и
  не ответ в тот же тред, как `isFirstReply` веб-клиента) — кликабельная
  строка контекста «Ответ <автору>: <фрагмент корня ≤ 80 символов>» («Ответ в
  треде», если корня нет в памяти — без дополнительного запроса).
- **Загрузки**: кнопка «⬇» в шапке канала (accessible name несёт число
  активных загрузок) открывает панель — список последних загрузок с
  прогрессом, «Открыть», «Показать в папке» и «Убрать из списка» на каждой
  строке, «Очистить список» внизу; Esc или клик вовне закрывает панель.
- **Редактор**: автодополнение `@`, `~`, `:эмодзи:`; Shift+Enter — перенос;
  ↑ — правка последнего своего; черновики по каналу и треду (черновик ответа
  — только в памяти, не больше 50). Вложения тоже по ключу (канал, корень):
  у композера канала и у композера каждого треда свой список и свои 10
  вложений; вложение ответа не уйдёт в пост канала, и наоборот.
- **Вложения** (стадия 3, часть 2; план `docs/plans/2026-09-27-stage3-attachments.md`;
  подробности и тесты — AGENTS.md): три источника — Ctrl+V (картинка из
  буфера или скрытый список файлов), перетаскивание в область канала, кнопка
  📎 (системный диалог выбора файлов). На desktop все три читает Go
  (WebKitGTK не отдаёт странице содержимое вставленного/перетащенного —
  спайк); browser-режим получает настоящие `File` и шлёт байты сырым телом
  на `/api/attachments`. Лимиты — `EnableFileAttachments` и `MaxFileSize`
  (по умолчанию 100 МиБ) с сервера, не больше 10 вложений на пост;
  превышение — сообщение у композера, вложение не добавляется. Загрузка на
  сервер Mattermost начинается сразу после добавления, пока воркер «живой»;
  офлайн — вложение ждёт с чипом прогресса. Ошибка загрузки не повторяется
  автоматически (правило «POST не повторяются на сетевых ошибках») — чип
  «Ошибка» с «Повторить». Отправка допускает вложения без текста; ожидающий
  пост с ещё не загруженными вложениями ждёт **без ограничения по времени**
  (в отличие от текстового поста, который считается неотправленным через
  30 с) — офлайн с вложением может длиться сколько угодно, лишь бы вложения
  в итоге догрузились. Вложения и ожидающие с ними посты не переживают
  перезапуск клиента (как и обычные ожидающие посты сегодня) — `docs/backlog.md`.
  Безопасность: UI ни в одном методе API не передаёт в Go пути — только
  сервер/канал; каждый источник требует нативного действия пользователя,
  которое страница подделать не может (нажатая клавиша вставки, drop только
  из **другого** приложения, клик в модальном системном диалоге); файлы
  каталога данных приложения никогда не вкладываются. Принятый остаточный
  риск: настоящий drag из другого приложения на страницу с подделанным
  `text/uri-list` — это обычный внешний drop и он принимается; использовать
  его для эксфильтрации всё равно нужна XSS в самом клиенте (AGENTS.md,
  «модель угроз»).
- **Поиск**: серверный (`posts/search`), с переходом к сообщению в контексте.
- Ctrl+K — быстрый переход по каналам/DM/тредам всех серверов.
- Светлая/тёмная тема, по возможности синхронизация с темой пользователя на
  сервере. Статусы присутствия, «печатает…». UI на русском и английском.
- Тёмная тема — из коробки, по умолчанию: без настройки, без зависимости от
  `prefers-color-scheme` (WebKitGTK отдаёт его ненадёжно); токены — в
  `frontend/src/index.css` (task 14b).

Стек фронта — как у соседних проектов: React 19, Vite, TypeScript, Tailwind 4,
Zustand, без UI-библиотеки, pnpm. Навигация — через store, без роутера.
Markdown — `react-markdown` + `remark-gfm` с санитизацией; подсветка кода
загружается лениво.

## Вход и безопасность

### Вход через GitLab

1. «Добавить сервер» → URL → проверка `system/ping` и `config/client`.
2. «Войти через GitLab» → системный браузер на
   `/oauth/gitlab/mobile_login?redirect_to=mmauth://callback`.
3. Сервер после входа отдаёт страницу с редиректом на
   `mmauth://callback?MMAUTHTOKEN=…&MMCSRF=…&srv=…`. ОС передаёт ссылку
   приложению; single-instance доставляет её в запущенный экземпляр. Клиент
   сверяет `srv` с сервером, для которого начат вход, сохраняет токен.
4. 401 или провал WS-аутентификации → сервер в состоянии «нужен вход»; кэш
   остаётся читаемым; в UI — «Войти снова». «Выйти» отзывает сессию на
   сервере (`users/logout`).
5. Вход по логину/паролю тоже поддерживается (дёшево, пригодится для других
   серверов).

Регистрация `mmauth://`: Linux — `.desktop` с
`MimeType=x-scheme-handler/mmauth`; Windows — реестр из msi; macOS —
`CFBundleURLTypes`. Официальный Mattermost Desktop использует `mattermost://`,
конфликта нет.

Сессия создаётся сервером как мобильная (`action=mobile`), срок жизни —
по `SessionLengthMobileInHours` сервера.

### Хранение токенов

Решение пользователя: **токены в SQLite** (таблица `servers`), без keyring и
без мастер-пароля. Обоснование: keyring на Linux/Windows не защищает от
процессов того же пользователя, при выполненном входе он уже разблокирован,
кража диска закрывается шифрованием диска, а цена — зависимость от
D-Bus/gnome-keyring и ровно тот класс зависаний, что сломал официальный
клиент. Токен восстанавливаем: отзывается «Выйти» или в «Активных сессиях»
профиля Mattermost.

- Файлы базы и кэша — права 0600, каталог — 0700.
- `servers` отделена от таблиц кэша: «сбросить кэш» и пересоздание битого
  снимка не трогают вход. Если база повреждена целиком — пересоздаётся, клиент
  просит войти снова.
- Токен не попадает во фронт, в логи (маскируется) и в диагностические
  выгрузки; отправляется только на выдавший его сервер.
- HTML/markdown постов и превью ссылок санитизируются; внешние ссылки
  открываются в системном браузере.

## Упаковка и обновления

По образцу citeck-launcher:

- Linux: deb, rpm (nfpm) + AppImage; Windows: msi (WiX, `-H windowsgui`);
  macOS: dmg, подпись и нотаризация при наличии сертификата, иначе ad-hoc.
- CI (GitHub Actions): гейт (vet, golangci-lint, `-race`, vitest, govulncheck)
  + матрица релизов по тегу `v*.*.*`.
- Автообновление: GitHub Releases, sha256 + ed25519-подпись, установка по
  подтверждению пользователя.
- Single-instance: повторный запуск (и приход `mmauth://`) передаёт управление
  первому экземпляру.
- Автозапуск со свёрнутым в трей окном (опция).

## Тестирование

- **Go**: testify + `httptest`-фейки REST/WS: ретраи, 429, resume по seq,
  дыры в истории, правила уведомлений, отложенная запись снимка.
- **`internal/mmfake`**: фейк-сервер с нужным подмножеством API и событий;
  им же питается браузерный режим для e2e.
- **Фронт**: Vitest + Testing Library (компоненты, markdown, редактор).
- **E2E**: Playwright против браузерного режима с mmfake: вход, переключение
  каналов, треды, реакции, файлы, поиск, уведомления, переподключение;
  скриншотные проверки.
- **Живые тесты** на реальном сервере — вручную под `SPK_MM_LIVE=1`.
- **Бюджет памяти как тест**: сценарий «100 каналов + час активности» из
  mmfake, замер суммарного Private_Dirty (`scripts/pss.sh`); падает при
  устойчивом росте, превышение ориентира ~150 МБ разбирается отдельно.

  адресом (GLib/WebKit падают сразу, а не висят), а закрытие окна
  завершает приложение (без трея окно было бы не вернуть). Слушатель темы
